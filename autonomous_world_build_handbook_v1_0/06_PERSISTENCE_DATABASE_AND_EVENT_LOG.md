# Persistence, Database, and Canonical Event Log

**Version:** 1.0  
**Status:** Normative persistence design  
**Database:** PostgreSQL with pgvector  
**ORM:** SQLAlchemy 2 typed declarative mapping  
**Driver:** Psycopg 3 async  
**Migrations:** Alembic

---

## 1. Persistence goals

The persistence layer must provide:

- one authoritative canonical world;
- short atomic scene/event commits;
- immutable historical provenance;
- efficient current-state queries;
- strict character-memory isolation;
- optimistic concurrency;
- idempotent retry handling;
- durable asynchronous work through an outbox;
- migration and rebuild paths;
- exact vector search during early stages;
- enough audit data to explain every important outcome.

It must not become a generic dumping ground for model JSON. Data that drives rules, filtering, permissions, relationships, retrieval, or UI behaviour belongs in typed columns and relational tables.

---

## 2. Database topology and schemas

Use one PostgreSQL cluster and one application database initially.

Recommended schemas:

```text
worldsim                 Canonical domain, operational tasks, read projections.
langgraph_checkpoint     LangGraph checkpointer tables when durable graph state is enabled.
observability            Optional local trace/metric metadata if stored in PostgreSQL.
```

Temporal, when introduced, manages its own database/schema according to Temporal deployment guidance. Do not mix Temporal internal tables with `worldsim` tables.

Enable extensions in the first migration:

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS pgcrypto;
```

Application IDs are generated in Python as UUIDv7-compatible UUID values. Do not depend on a specific PostgreSQL major version for UUIDv7 generation.

## 3. Naming and type conventions

### 3.1 Tables and columns

- lower snake case;
- plural table names are not required, but this project uses singular domain table names consistently;
- primary key column: `id`;
- foreign keys: `<referenced_concept>_id`;
- operational timestamps: `created_at`, `updated_at`, `started_at`, `completed_at`, `failed_at` as `timestamptz`;
- fictional ordering: `absolute_phase_index bigint` and explicit calendar fields;
- optimistic version: `version bigint not null default 1`;
- soft lifecycle: `status text` plus `archived_at`, not a generic `is_deleted`;
- content hashes: lowercase hexadecimal SHA-256 text or `bytea`, chosen consistently by implementation ADR;
- model/provider payloads: `jsonb` only at external/provenance boundaries.

### 3.2 Constraint naming

Configure SQLAlchemy metadata naming conventions and never rely on autogenerated anonymous names:

```python
NAMING_CONVENTION = {
    "ix": "ix_%(table_name)s_%(column_0_N_name)s",
    "uq": "uq_%(table_name)s_%(column_0_N_name)s",
    "ck": "ck_%(table_name)s_%(constraint_name)s",
    "fk": "fk_%(table_name)s_%(column_0_N_name)s_%(referred_table_name)s",
    "pk": "pk_%(table_name)s",
}
```

Every `CheckConstraint` receives an explicit logical name so Alembic output is deterministic.

### 3.3 Enumerations

Use Python `StrEnum` at the domain boundary and `text` columns with named `CHECK` constraints for vocabularies expected to evolve. Avoid PostgreSQL-native enums for action families, statuses, event types, and memory types unless a future ADR justifies the migration friction.

### 3.4 JSONB policy

JSONB is appropriate for:

- provider request/response metadata;
- model capability snapshots;
- context manifests;
- structured facts whose keys are event-type-specific and not used for core constraints;
- visual workflow parameters;
- audit detail;
- typed payload snapshots retained alongside normalized data.

JSONB is not appropriate as the only representation for:

- current location;
- stamina/mana;
- life status;
- relationships;
- world clock;
- ownership;
- task state;
- memory owner/visibility;
- event sequence;
- action participants/targets;
- fields routinely filtered or joined.

## 4. Event-log and projection strategy

Use a hybrid model:

```text
Immutable canonical history
  world_event
  event_participant
  event_effect
  observation
  claim
  user_command audit

Mutable current projections
  world_clock
  character_state
  relationship_state
  belief
  activity
  inventory_entry
  faction_state
  world read models
```

Each scene/event transaction inserts history and updates projections together. Current projections are not authoritative without their associated source history, but normal reads do not replay the entire event log.

Projection rebuild tooling must be introduced before Stage 3 promotion for core state. It may initially rebuild a subset—clock, character state, relationships, and active activities—from a clean snapshot plus later events.

### 5.1 `world`

Purpose: root aggregate and event-sequence allocator.

| Column | Type | Rules |
|---|---|---|
| `id` | uuid PK | Application-generated. |
| `slug` | text | Unique, immutable after creation. |

| `language` | text | Initially `en`. |
| `content_rating` | text | Initially `young_adult_soft_dark`. |

- unique `slug`;
- status check;
- `current_event_sequence >= 0`;
- ended/status consistency;
- partial unique index allowing only one row with `status in ('initializing','active','paused')` for the initial single-world product.

- optional trigger rejects updates/deletes unless a session-local migration flag is set.

## 18. Canonical scene commit algorithm

Pseudocode:

```python
async def commit_scene_resolution(command: CommitSceneResolution) -> CommitResult:
    # Remote model work has already completed.
    async with transaction_manager.begin() as tx:
        existing = await resolution_repo.find_committed_by_idempotency_key(
            command.idempotency_key,
            for_update=False,
        )
        if existing is not None:
            return CommitResult.from_existing(existing)

        world = await world_repo.lock(command.world_id)
        scene = await scene_repo.lock(command.scene_id)

        assert scene.state == SceneState.READY_TO_COMMIT
        await aggregate_versions.verify(command.expected_versions)
        validated_effects = domain_effect_validator.validate_all(
            command.effects,
            current_state=await state_loader.for_effects(command.effects),
        )

        sequence = world.current_event_sequence + 1
        event = await event_repo.insert(
            sequence_number=sequence,
            idempotency_key=command.idempotency_key,
            phase_run_id=command.phase_run_id,
            scene_id=command.scene_id,
        )

        for index, effect in enumerate(validated_effects):
            before, after, new_version = await effect_applier.apply(effect, event.id)
            await event_effect_repo.insert(event.id, index, effect, before, after, new_version)

        observations = perception_engine.materialize_allowed_observations(event, validated_effects)
        await observation_repo.insert_many(observations)
        await memory_repo.insert_immediate_candidates(observations)
        await outbox_repo.insert_many(build_outbox(event, observations))

        await scene_repo.mark_committed(scene.id, event.id)
        await world_repo.advance_event_sequence(world.id, sequence)

    return CommitResult(event_id=event.id, sequence_number=sequence)
```

Important:

- validation occurs both before and inside the transaction;
- inside-transaction validation uses current versions;
- no model call occurs inside;
- duplicate idempotency returns the prior result;
- observation wording may be generated before commit only if it is constrained and included in the transaction; otherwise commit fact envelopes and generate phrasing asynchronously without changing allowed facts.

---

## 19. Isolation levels and locking

Default transaction isolation may remain PostgreSQL `READ COMMITTED` if:

- affected aggregates are explicitly locked or version-checked;
- scene conflicts are assembled before resolution;
- unique constraints protect idempotency and sequence allocation;
- retries handle serialization/unique races.

Use `SELECT ... FOR UPDATE` for:

- world event sequence allocation;
- scene state transition to commit;
- mutable aggregate rows with effects;
- task/outbox claims.

Avoid broad table locks. Keep commit transactions short.

Advisory locks may protect one phase leader per world, but they are not substitutes for idempotency and row constraints.

## 20. Retrieval query shape

Initial exact memory search:

```sql
SELECT
    m.id,
    m.content,
    m.salience,
    m.confidence,
    m.occurred_phase_index,
    1 - (me.embedding <=> CAST(:query_embedding AS vector)) AS semantic_similarity
FROM worldsim.memory AS m
JOIN worldsim.memory_embedding AS me ON me.memory_id = m.id
WHERE m.world_id = :world_id
  AND m.owner_character_id = :owner_character_id
  AND m.status = 'active'
  AND m.created_phase_index < :current_phase_index
  AND me.is_active = true
  AND me.embedding_model_key = :embedding_model_key
  AND me.embedding_version = :embedding_version
ORDER BY me.embedding <=> CAST(:query_embedding AS vector)
LIMIT :candidate_count;
```

Mandatory owner and world filters are never removed to improve recall. Hybrid reranking happens in application code over the candidate set.

When HNSW is later introduced, filtered approximate retrieval must be validated carefully because approximate indexes apply filtering after index scanning. Use exact search as a correctness oracle, and consider partial indexes/partitioning or iterative scans only after measured need. See the official pgvector guidance referenced in `33_REFERENCE_REGISTRY_AND_CHANGE_CONTROL.md`.

## 21. Index strategy

### Stage 0–1

- PK and FK indexes;
- unique idempotency keys;
- phase/world status partial indexes;
- event sequence/timeline indexes;
- character observation/recent memory indexes;
- no approximate vector index.

### Stage 2–3

Add after `EXPLAIN (ANALYZE, BUFFERS)` evidence:

- active task/outbox claim partial indexes on `(available_at, priority)`;
- relationship and belief owner indexes;
- memory owner/time/type indexes;
- GIN indexes only for JSONB keys that have demonstrated query use;
- text search/trigram indexes for entity deduplication;
- possibly HNSW on active memory embeddings if exact search fails the target.

Do not create an index for every column. Document the query each index supports.

## 23. Seed and bootstrap policy

Initial seed data may have `created_event_id = NULL` only during bootstrap revision/command. Immediately after seeding:

- create a `WORLD_INITIALIZED` event;
- attach seed manifest hash;
- mark the world active;
- prohibit further null source events for ordinary mutations.

A seed is repeatable and keyed by a `seed_version`. Rerunning it on an initialized world must fail or be idempotently recognized; it must not duplicate characters or locations.

## 24. Backup, restore, and projection rebuild

Before Stage 3:

- daily logical database backup in development soak runs;
- backup object-storage metadata/assets separately after Stage 4;
- record application version, migration head, prompt registry hash, and model profiles with backup metadata;
- test restoration into a separate database;
- verify event counts, latest sequence, current clock, and projection hashes;
- maintain a command to rebuild selected projections from a snapshot/event range.

A backup that has never been restored is not considered valid.

## 25. Database test matrix

Mandatory tests include:

- only one active world;
- unique event sequence under concurrent commit attempts;
- duplicate resolution idempotency returns one event;
- stale aggregate version rejects commit;
- phase snapshot cannot be changed after sealing;
- one primary action per actor/phase;
- one active primary activity per character;
- non-negative bounded resources;
- owner filter blocks another character’s memory;
- event/history rows reject runtime update/delete;
- outbox exists whenever a canonical event requires async work;
- worker lease expiry permits reclaim;
- migration upgrade/downgrade/upgrade succeeds;
- projection rebuild matches known fixture state;
- hard retcon marks dependent state/audit status without deleting history.

## 26. Implementation boundaries

Repositories expose domain-oriented methods, not generic `save()` everywhere.

Good:

```text
world_repository.lock_for_event_sequence(world_id)
scene_repository.mark_ready_to_commit(scene_id, expected_version)
event_repository.find_by_idempotency_key(key)
memory_repository.search_owner_candidates(query)
task_repository.claim_available(worker_id, lease_duration)
```

Bad:

```text
repository.execute_arbitrary_sql(...)
repository.save(dict_payload)
agent_tool.update_character_state(...)
model_output.apply_to_session(...)
```

The transaction service, not a LangGraph node or API route, owns the unit of work.
